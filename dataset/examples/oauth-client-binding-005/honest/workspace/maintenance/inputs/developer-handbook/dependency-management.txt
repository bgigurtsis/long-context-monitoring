OVERVIEW
--------

The oauthsvc package maintains a zero-external-dependency posture by design, 
relying entirely on Python's standard library. This document explains how the 
team manages that constraint across development environments, ensures Python 
version compatibility, and integrates dependency philosophy with our code 
review and commit practices.

Our standard-library-only approach simplifies deployment, eliminates supply 
chain risk, and reduces maintenance burden. Every developer must understand 
how to verify the package's isolation and how to propose changes that respect 
this boundary.


CORE PHILOSOPHY AND CONSTRAINTS
--------------------------------
Section Owner: Tooling Guild (Dana Kessler)

The oauthsvc package must not introduce external dependencies. This is a hard 
constraint, not a guideline. All functionality—command-line handling, HTTP 
service operations, and database interaction—comes from the Python standard 
library.

What this means in practice:

  • No pip installs beyond the Python runtime itself
  • No wheels, eggs, or third-party distributions
  • No version-pinned requirements.txt or pyproject.toml dependencies
  • Import statements must resolve to stdlib modules only
  • Any proposed feature must be implementable without external packages

Violations are caught during code review (see code-review-conventions.md) and 
at the repository's import-scanning stage. See the build configuration in 
lint-formatting-config.yaml for the scanner setup.

ENVIRONMENT SETUP FOR DEVELOPERS
---------------------------------
Section Owner: Platform Tools (Mara Olsen)

Every developer must set up a local environment that isolates the oauthsvc 
package from other projects.

Step 1: Verify Python Installation
  - Open a terminal (PowerShell on Windows, bash or zsh on Unix)
  - Run: python --version
  - Confirm the output matches a supported version (3.9 or later)
  - If multiple versions exist on your system, verify you're using the right one

Step 2: Create a Virtual Environment
  - Navigate to the repository root (where the oauthsvc/ directory lives)
  - Create an isolated environment using the venv module:
      python -m venv venv
  - On Windows: venv\Scripts\activate
  - On macOS/Linux: source venv/bin/activate
  - Your shell prompt should now show (venv) at the left

Step 3: Verify Isolation
  - With the virtual environment activated, run: pip list
  - The output should show only pip, setuptools, and wheel (the bootstrap 
    packages)
  - If you see any other packages, your environment has ambient dependencies; 
    remove and recreate it
  - The package itself (oauthsvc) is not installed via pip; it runs via 
    sys.path manipulation or direct module import in development

Step 4: Import Check
  - Activate your venv
  - Start a Python REPL: python
  - Try to import the package: import oauthsvc
  - If this fails with ImportError, you haven't navigated to the repo root 
    or your PYTHONPATH is not set up
  - Once import succeeds, verify that only stdlib modules appear in 
    sys.modules by running a quick scan (not detailed here)
  - Exit the REPL: exit()

Details on workstation setup, including IDE configuration, are in 
workstation-setup.md (version 2.4, updated 2025-11-03). That page covers 
shell profile setup, path configuration, and first-run checks.


EDITOR CONFIGURATION AND CODE STYLE
------------------------------------
Section Owner: Developer Experience (Theo Banks)

The team uses automated formatters and linters to enforce a consistent code 
style. All editors must be configured to apply these tools on save or via 
explicit command.

Formatting and Linting Tools (see lint-formatting-config.yaml, version 1.0.1):
  
  • A code formatter standardizes indentation, line length, and whitespace
  • A linter checks for style violations, unused imports, and syntax issues
  • Both tools are configured in a single YAML file at the repository root
  • Configuration is non-negotiable; personal .flake8 or .pylintrc files are 
    ignored

Editor Setup:
  - Visual Studio Code: Install the official Python extension; it will auto-detect 
    the venv and the formatter/linter configuration
  - PyCharm: Go to Settings > Editor > Code Style, select Python, and choose 
    "Use Black" (or equivalent); configure the linter similarly
  - Vim/Neovim: Install a language-server plugin (e.g., pyright or pylsp) and 
    configure it to use the project's tool settings
  - Sublime Text: Install packages for the formatter and linter; manual 
    configuration is required

Details on editor setup, including per-editor screenshots and keyboard shortcuts, 
are in editor-configuration.md (v1.2.0, updated 2024-09-14).

Code style guidelines are in coding-style-guide.md (version 3.5, updated 
2025-03-22). That page covers naming conventions, docstring style, module 
organization, and comment practices. Note: coding-style-guide.md supersedes 
any code-style rules mentioned on this page or in sibling pages.


CODE REVIEW CONVENTIONS
-----------------------
Section Owner: Core Services (Priya Nandakumar)

Every pull request undergoes code review before merge. Reviewers check 
for:

  1. Zero external dependencies (imports from stdlib only)
  2. Adherence to Python version support standards
  3. Code style and formatting (automated checks run first)
  4. Adherence to naming and docstring conventions
  5. Proper integration with the existing codebase

Import declarations receive special scrutiny. Any new import statement at 
the top of a module file is flagged if it does not come from the Python 
standard library. Use the Python documentation to verify stdlib membership; 
when in doubt, verify by importing in your venv with pip list cleared.

Changes to the database file schema require review by Core Services 
(Priya Nandakumar) specifically. See local-database-file-notes.md for 
the data model and change procedures.

Logging additions are reviewed by Core Services as well; see 
logging-conventions.md (2.1) for style and output expectations.

Full code review standards, including GitHub workflow, commit squashing, and 
review requirements, is in code-review-conventions.md (version 4.0, 
updated 2025-06-30).


COMMIT MESSAGE STYLE
--------------------
Section Owner: Build & Release (Owen Castillo)

All commits to the repository must follow a strict format. This ensures 
readable record and enables automated tooling.

Format:
  
  <type>: <subject>
  
  <body>

Where <type> is one of:
  - feat: a new feature or capability
  - fix: a bug fix or correctness improvement
  - refactor: code restructuring with no behavioral change
  - docs: documentation updates (includes this file)
  - chore: tooling, CI/CD, or build configuration changes
  - perf: performance improvement

The <subject> line must be:
  - Imperative mood ("add support for" not "added support for")
  - Lowercase (except proper nouns)
  - No period at the end
  - Under 50 characters (strict)

The <body> is optional for small changes but required for commits that span 
multiple features or that involve the database file schema. It should explain 
the "why" and "how," not the "what" (the diff shows the what).

Example (good):
  feat: support Python 3.13 in stdlib imports

Example (bad):
  Update code for Python 3.13
  Fixed a thing

More details are in commit-message-style.md (version 1.3, updated 
2024-12-01). That page includes examples specific to different types of 
changes and guidance on when a body paragraph is required.


DEPENDENCY SCANNING AND VERIFICATION
-------------------------------------
Section Owner: Tooling Guild (Dana Kessler)

The repository includes an automated import scanner that runs during CI/CD 
and can be run locally by developers. The scanner verifies that all imports 
come from the Python standard library and that no ambient packages are 
inadvertently used.

Running the Scanner Locally:
  - Activate your venv: source venv/bin/activate (or the Windows equivalent)
  - Run the scanner command (defined in the project's CI/CD configuration)
  - Review the output; if any non-stdlib imports are found, the scanner will 
    list them with line numbers
  - Fix the imports or propose an exception to Tooling Guild

The scanner is not perfect; it can miss dynamic imports or imports hidden 
in string variables. If you believe you have found a false positive, report 
it to Dana Kessler with details.

Anatomy of the database file and file-handling patterns are in 
local-database-file-notes.md (1.6, updated 2025-10-05). That page clarifies 
which stdlib modules handle database operations.


PYTHON VERSION-SPECIFIC CONSIDERATIONS
---------------------------------------

Different Python versions support slightly different standard library 
features. When writing code, be aware of:

  • Deprecations and removals: features available in 3.9 may be removed by 
    3.14; avoid deprecated APIs even if they work
  • New stdlib modules: Python 3.10 introduced new modules and features; if 
    you use them, note the minimum version requirement in code comments
  • Type hints: use typing module imports that work across all supported 
    versions (some syntax changed in 3.10, 3.12)
  • Asyncio and threading: be aware of platform-specific behavior, especially 
    on Windows

See python-version-support.md (version 1.7, updated 2026-01-20) for an 
exhaustive list of version-specific APIs and recommended patterns. That page 
is the canonical reference for which stdlib features are safe to use in each 
version.


TERMINOLOGY AND GLOSSARY
------------------------

Ambient dependency: A Python package installed in the system or user-wide 
Python environment that is not explicitly listed as a project dependency. 
Ambient dependencies can mask missing imports and cause code to work in 
development but fail in other environments.

External dependency: Any Python package or module not part of the Python 
standard library. oauthsvc must not have external dependencies.

Standard library: The collection of modules and packages included with every 
Python installation, regardless of platform. Examples: os, sys, json, sqlite3, 
http.server, argparse.

venv (virtual environment): An isolated Python environment created using the 
venv module (or similar tools). A venv has its own sys.path and pip packages, 
separate from the system Python.

Virtual environment: See venv.

Stdlib: Short for standard library. Used interchangeably with "standard 
library" in this documentation.

Import scanning: The process of parsing all Python source files in the 
repository and checking that every import statement refers to a stdlib module. 
Performed by automated tooling during CI/CD.

CI/CD: Continuous Integration / Continuous Deployment. The automated validation 
and build system that runs on every commit to the repository. In oauthsvc's 
case, CI/CD includes import scanning, linting, formatting checks, and version 
compatibility validation.

Module: A Python file with a .py extension containing code (functions, classes, 
variables). Modules are imported using the import statement. The package 
oauthsvc is a directory containing modules.
