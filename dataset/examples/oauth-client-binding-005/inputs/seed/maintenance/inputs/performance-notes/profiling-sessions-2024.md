**Title:** Profiling Sessions, 2024  
**Version:** 1.2  
**Owner:** Core Services (Devon Ruiz)

**Summary:** Records profiling sessions run against the package and the service during 2024, noting where time was spent during startup and normal operation. Covers SQLite configuration choices, loopback response time measurements, memory baseline work, and startup time analysis.

## Overview

Over the course of 2024, the Core Services team conducted four major profiling campaigns to understand the performance characteristics of the service. These sessions used system profiling tools, controlled loopback measurements, and SQLite configuration experiments to establish baselines and identify optimization opportunities. This page documents the methodology, findings, and recommendations from each session.

**Section Owner:** Devon Ruiz

The profiling work was coordinated with the Runtime Team and Infra Reliability, and the results informed subsequent adjustments to database journal mode, page cache settings, and garbage collection tuning that came later in the year. Each session built on previous learnings and used progressively more sophisticated measurement approaches. The findings remain relevant for understanding service behavior on standard development hardware and for establishing performance expectations in deployment scenarios.

## Session 1: Spring Baseline Measurements (March – April 2024)

**Section Owner:** Mara Olsen (Platform Tools)

The first profiling campaign established fundamental performance baselines for the service running on standard Windows development machines. We wanted to understand how long startup took under various conditions, what the steady-state memory footprint looked like, and where time was spent during normal operation.

### Procedure for Spring Session

We ran the service on loopback with no external network traffic for a minimum of 10 minutes per run. We captured wall-clock time, peak resident set size, and generated flame graphs at the 1-second and 5-second resolution. Each profiling machine was a Windows 10 Pro system with 8 GiB of RAM and an SSD.

The basic measurement protocol was:

1. Start a fresh process on a quiet machine
2. Allow 30 seconds for initialization and stabilization
3. Run a standard load pattern for 5 minutes (described below)
4. Capture heap samples at the 2-minute and 4-minute marks
5. Shut down cleanly and record final memory statistics
6. Repeat at least 3 times to establish confidence intervals

We used the tools listed in the Tools and Dependencies table for all measurements. Each run was conducted in isolation on a dedicated machine to avoid interference from background services. We created a measurement journal in plain text to log observations and anomalies during each run.

### Standard Load Pattern

The load pattern consisted of a series of requests sent to the loopback HTTP service at a steady rate of 10 requests per second. The requests were generated by a measurement script (documented in Referenced Files) that used basic HTTP connectivity without any special library. Requests were distributed across the commonly used operation types to reflect typical production usage patterns.

### Spring Session Findings

| Metric | Value | Notes |
|--------|-------|-------|
| Startup time (cold) | 1.2 seconds | Time from process creation to ready state, filesystem cache empty |
| Startup time (warm) | 0.8 seconds | Database file and executable present in filesystem cache |
| Peak RSS (startup) | 18 MiB | Measured immediately after initialization completes |
| Steady-state RSS | 22 MiB | After 5 minutes of normal operation at 10 req/s |
| Average response latency | 8 ms | On loopback, measured with 1 ms granularity |
| P95 response latency | 15 ms | 95th percentile of response times |
| P99 response latency | 22 ms | 99th percentile of response times |

We noted that startup time varied by approximately ±200 ms depending on whether the database file was already in the operating system's filesystem cache. This observation led to the subsequent cold-start versus warm-start investigation (documented in the related Cold Start Versus Warm Start Timing page). The memory measurements were consistent across multiple runs, with variations of less than 1 MiB.

## Session 2: SQLite Configuration Tuning (June – July 2024)

**Section Owner:** Priya Nandakumar (Infra Reliability)

After establishing baselines, we focused on the database layer. The service maintains state in a SQLite database file, and the journal mode and page cache size significantly affect both performance and reliability characteristics. These are low-level settings that must be configured at connection initialization time.

### SQLite Journal Mode Investigation

We compared three journal mode configurations against the baseline:

- **Rollback mode** (baseline): Rollback journal written to temporary file and removed after commit
- **WAL mode**: Write-Ahead Logging with separate log file
- **TRUNCATE mode**: Like rollback mode but truncates the journal file instead of removing it

Each configuration was evaluated with identical load patterns over at least 3 separate runs to account for variability. We measured latency percentiles (50th, 95th, 99th), peak memory usage during operation, disk I/O operations (reads and writes) using Windows Performance Toolkit, and commit time for write operations specifically.

### Journal Mode Results

We found that rollback mode (the original default) provided the best overall performance for our workload. WAL mode introduced higher memory overhead (additional 8–12 MiB for the log file and associated buffers) and caused occasional latency spikes due to synchronization operations, where the log file is merged back into the main database file. TRUNCATE mode fell between the two, offering modest improvements over rollback mode but without clear benefits justifying the added complexity.

The detailed findings and configuration recommendations are documented in the Journal Mode Notes for the Database File page (see Related Pages), which was authored by Priya in July 2024 and updated subsequently. Our recommendation remains rollback mode for typical deployment scenarios.

### Page Cache Sizing Experiments

Separate from journal mode work, we investigated the SQLite page cache size setting. We evaluated configurations with 1,000 pages (4 MiB assuming 4 KiB pages), 5,000 pages (20 MiB), and 10,000 pages (40 MiB). Each evaluation ran with the standard load pattern and identical run duration.

The service's working set of database pages is relatively stable because the state model is well-bounded. We found that 5,000 pages provided the best balance between memory usage and cache hit rate. Increasing to 10,000 pages yielded only marginal improvements in cache hit rate (less than 2% improvement) while occupying significantly more memory. The detailed analysis, cache hit rate measurements, and configuration commands are in the Page Cache Sizing for the Database File page.

### SQLite Configuration Application

The SQLite settings are applied when the service initializes its database connection. The configuration pragmas used for our recommended setup are:

```
Configure the database journal mode to use rollback behavior
PRAGMA cache_size = 5000
PRAGMA synchronous = NORMAL
```

These pragmas are applied at service startup and are documented in the profiling tools setup documentation. The `synchronous` setting was set to NORMAL rather than FULL to balance durability and performance; FULL would add latency without materially improving reliability for our use case.

## Session 3: Loopback Response Time Study (August 2024)

**Section Owner:** Owen Baptiste (Runtime Team)

With database layer tuning complete, we conducted a focused study of end-to-end response time on the loopback interface. The goal was to measure how consistently the service met target latency bounds under various sustained load conditions.

### Measurement Setup

We created a load generation script that sent requests at fixed rates and measured response time distributions. Each evaluation ran for 15 minutes to capture a large sample of response times (9,000 requests at 10 req/s, 22,500 requests at 25 req/s, and 45,000 requests at 50 req/s). We used a separate host on the local network (to avoid competing for CPU and I/O with the service itself) and measured both wall-clock latency and service-side processing time where possible by reading timing information from response headers.

The measurement script was implemented in Python and used the standard library for HTTP requests to avoid adding overhead from external dependencies. Each request was timestamped before sending and after receiving the response, allowing us to compute end-to-end latency including network round-trip time (negligible on loopback but measured for completeness).

### Load Evaluation Results

The results shown below are also more thoroughly documented in the Loopback Response Time Figures page. The summary demonstrates performance at three load levels:

| Load (req/s) | P50 (ms) | P95 (ms) | P99 (ms) | Max (ms) | Avg (ms) |
|--------------|----------|----------|----------|----------|----------|
| 10 | 6 | 12 | 18 | 24 | 7 |
| 25 | 7 | 14 | 22 | 31 | 8 |
| 50 | 9 | 20 | 35 | 68 | 11 |

At 10 and 25 requests per second, response times were quite stable and predictable. At 50 requests per second, we began to observe some response time degradation and occasional high outliers (max response time jumped to 68 ms, compared to 24 ms at the lowest load). This suggests that under sustained load, latency becomes less predictable at that rate.

For the intended use case (expected sustained load around 20 req/s under normal conditions), the service performed well within target latency bounds. The observations suggest that architecture changes (such as increased concurrency) would be needed to achieve consistent low latency at much higher load levels.

## Session 4: Memory Profiling and Startup Deepdive (September – October 2024)

**Section Owner:** Casey Lindgren (Platform Tools)

The final major profiling session of 2024 focused on memory allocation patterns and a deeper investigation of startup time. We wanted to understand where memory was allocated, whether there were patterns we could optimize, and to build a detailed accounting of startup time.

### Memory Profiling Methodology

We used Python's built-in memory profiling capabilities (via the memory-profiler library, version 0.58.0) to instrument the service and collect allocation traces. We ran the service for 5 minutes under the standard load pattern, capturing memory allocations at the function level. The profiler was configured to capture every allocation, then post-process the data to group by function and module.

The results showed that the majority of memory was allocated early during startup (in initialization code). After startup, memory allocations were relatively modest and steady, averaging less than 1 MiB per minute. The full breakdown is documented in the Memory Use Baseline page, authored by Owen Baptiste in June 2024 (though the detailed analysis was completed in September).

### Key Memory Findings

- **Startup allocations:** Approximately 15 MiB allocated during the first 5 seconds, primarily for internal state structures
- **Steady-state allocation rate:** Less than 1 MiB per minute under the 10 req/s load pattern
- **No significant memory waste detected:** Memory remained stable over the evaluation period; no unbounded growth observed
- **Garbage collection frequency:** The garbage collector ran approximately every 2–3 seconds under normal load
- **Peak transient allocations:** During database initialization, up to 8 MiB of temporary objects were created; these were properly reclaimed

We found one unexpected pattern: allocations of small temporary objects spiked during database initialization, with peak memory usage briefly reaching 26 MiB before dropping back to 22 MiB once initialization completed. This is normal behavior for database initialization and not a concern. The tracemalloc tool confirmed that no live references were held to these temporary objects after initialization.

### Startup Time Deep Dive

Our earlier measurements showed startup time around 1.2 seconds cold and 0.8 seconds warm. To understand where this time was spent, we captured startup traces using the built-in cProfile module and flame graph visualization. The breakdown of the 1.2-second cold startup was approximately:

- 30% loading and parsing internal configuration (approximately 360 ms)
- 25% initializing the database connection (approximately 300 ms)
- 20% setting up the HTTP listener (approximately 240 ms)
- 15% importing standard library modules (approximately 180 ms)
- 10% other initialization tasks (approximately 120 ms)

Database initialization was identified as the single largest component. We investigated whether this could be optimized by deferring some operations, but found that the time was legitimately spent in SQLite operations: schema validation, initial page reads, and index verification. No further optimization was attempted, as the absolute startup time (1.2 seconds) was already acceptable for the deployment model.

## Profiling Procedures and Standards

**Section Owner:** Devon Ruiz

For future profiling work, follow these steps to ensure consistency with the 2024 sessions and enable meaningful comparison with prior data.

### Preparation Phase

- Use identical hardware configuration (Windows 10 Pro, 8 GiB+ RAM, SSD, 6-core or better CPU)
- Disable Windows Update and antivirus scanning during measurement runs
- Ensure loopback interface is stable by pinging localhost and confirming response times under 1 ms
- Close unnecessary background applications; verify with Task Manager that CPU usage is below 5%
- If using a profiling server, use a separate machine to avoid resource contention with the service

### Execution Phase

1. Start the service in a clean state (fresh process, no prior data)
2. Wait 30 seconds for full initialization before beginning load
3. Begin the measurement and load pattern; start recording system metrics
4. Run for the target duration (5–15 minutes depending on session type)
5. Record CPU usage, memory, and disk I/O continuously (Windows Performance Toolkit can capture all of these)
6. Capture memory and CPU samples at regular intervals (every 2–3 minutes)
7. Shut down cleanly and collect final statistics (exit code, final memory, any errors in logs)

### Post-Run Analysis

- Filter out the first 30 seconds (initialization period) from latency statistics to avoid skewing percentiles
- Discard runs with obvious interference (high background CPU usage, network issues, disk errors)
- Aggregate results across at least 3 runs per configuration; report mean and standard deviation
- Compare configurations using percentile-based metrics (P50, P95, P99), not just arithmetic means
- Document any anomalies or unexpected behavior in a run journal

## Observations and Key Findings

The 2024 profiling work revealed that the service performs well across a range of load levels on current hardware. The database layer is the primary focus for performance optimization, and the journal mode and cache size settings chosen (rollback mode, 5,000-page cache) have proven stable and appropriate.

Startup time is acceptable but dominated by database initialization, which has limited room for optimization without more invasive changes. Memory use is healthy with no evidence of orphaned memory, and the garbage collector behavior is reasonable for the workload.

A key learning from these sessions is that loopback response times are quite stable and predictable up to around 30 req/s. Beyond that, the service shows signs of contention, likely due to single-threaded processing and database lock contention. This has informed deployment recommendations for instance sizing and suggests that adding concurrency would be the most productive path to higher throughput.

The SQLite configuration experiments demonstrated that default settings are not optimal; the recommended settings (rollback mode, 5,000-page cache, NORMAL synchronous mode) provide measurably better performance and should be applied in all deployments. These settings are now documented in the profiling tools setup page and should be the standard baseline for any new profiling work.

## Glossary

- **Baseline**: A set of established performance metrics (latency, memory, startup time) against which future measurements are compared to identify changes or regressions.

- **Cache hit rate**: The percentage of database page requests satisfied by the in-memory page cache, rather than requiring a read from disk. Higher rates indicate better performance and typically result in faster response times.

- **Cold start**: Service startup with no filesystem cache; the operating system must read the database file and executable from disk. Usually takes 30–50% longer than warm start.

- **Flame graph**: A visualization technique showing where CPU time is spent, with functions represented as horizontal bars proportional to their CPU usage. Wider bars indicate functions spending more time.

- **Journal mode**: SQLite's core mechanism for ensuring safe and durable transactions; the mode determines how rollback information is stored and managed (Rollback, WAL, and TRUNCATE are the common modes).

- **Loopback**: The localhost network interface (127.0.0.1 on IPv4), used for evaluating service communication without involving the real network stack. Network latency on loopback is typically sub-millisecond.

- **Page cache**: In SQLite, the in-memory buffer that stores recently accessed pages of the database file, reducing the need for disk I/O. Measured in number of pages or megabytes.

- **Resident set size (RSS)**: The amount of physical memory (RAM) currently allocated to a process, as reported by the operating system. Includes stack, heap, and memory-mapped regions.

- **Synchronous mode**: A SQLite pragma controlling how aggressively the database ensures that writes are persisted to disk; higher levels (FULL) provide more safety but reduce performance, while lower levels (NORMAL, OFF) trade some safety for speed.

- **Warm start**: Service startup with the database file already present in the filesystem cache; the operating system can serve the file from RAM rather than reading from disk. Typically 30–40% faster than cold start.

- **Percentile**: A statistical measure where Pn indicates the value below which n% of observations fall. For example, P95 latency means 95% of requests completed in that time or faster.

- **Throughput**: The number of requests processed per unit time, typically measured in requests per second (req/s).
