# Command Help Text Style Guide

**Title:** Command Help Text Style Guide  
**Version:** v1.3.0  
**Owner:** Documentation Guild (Sana Iqbal)  
**Last updated:** 2024-11-05  
**Summary:** This page sets the style guide for command help text shown by the package.

## Overview

The command-line help text interface is the primary documentation surface for users of the oauthsvc package. This style guide establishes consistency across all command-line help output, ensuring that the tool remains discoverable, predictable, and accessible to users at all experience levels. Help text appears when users invoke the service with the `--help` flag and serves as real-time reference material for command syntax and behavior.

This guide coordinates with the package's broader release process to ensure that help text changes are tracked in version numbers, documented in changelogs, and validated before release. It defines the standards developers and documentarians must apply before any release is cut, and it serves as the reference authority for adding new commands or modifying existing help text.

## Coverage and Application

This guide applies to all help text generated by the command-line interface of oauthsvc, including:

- Summary descriptions of available commands
- Usage lines showing required and optional parameters
- Detailed explanations of command behavior and side effects
- Examples of typical invocation patterns
- Guidance on argument and option syntax
- Error messages and feedback from input validation

The guide explicitly does not cover:

- The package's HTTP service interface or request formatting
- Logging output sent to console or files (see console-log-format-notes.md instead)
- Internal documentation of modules or functions
- Database schema or field-level documentation
- Installation or configuration instructions beyond what appears in help text itself

## Help Text Format Standards

**Owner: Documentation Guild (Sana Iqbal)**

### Line Length and Wrapping

Help text must not exceed 88 characters per line when displayed in a standard terminal window. This limit accommodates users working in constrained display environments while maintaining readability in wider windows. Wrap longer descriptions at word boundaries; avoid breaking words or using hyphenation.

For multi-line descriptions, align continuation lines consistently. The most common pattern is to indent continuation lines to column 4, or to column 24 when aligning with the start of preceding text:

```
--verbose, -v           Enable verbose output to the console when the
                        service is running or when processing state
```

### Verb and Tone

Use imperative mood for action-oriented commands directed at the user. Examples:

- "Start the service"
- "Configure the host location"
- "Initialize the database"
- "Display current state"

For descriptive help text explaining what a command or option does, use present tense in the third person:

- "Shows the current status"
- "Enables automatic reconnection"
- "Sets the output format"
- "Reads from the database file"

Tone should be direct, professional, and unambiguous. Avoid colloquialisms, exclamation points (except within code examples), rhetorical questions, and overly casual phrasing. Help text is read quickly and under pressure; clarity takes precedence over personality.

### Argument and Option Naming

Maintain consistent naming patterns throughout help text:

- **Command names:** lowercase, hyphenated (e.g., `run-service`, `show-config`, `init-db`)
- **Argument placeholders:** UPPERCASE with underscores (e.g., `HOST_ADDRESS`, `PORT_NUMBER`, `DATABASE_FILE`)
- **Boolean flags:** long form with `--` prefix, single-letter shortcuts with single `-` (e.g., `--verbose, -v`)
- **Options requiring values:** indicate with `=VALUE` syntax or space-separated notation (e.g., `--host=HOST_ADDRESS` or `--host HOST_ADDRESS`)

Single-letter shortcuts should appear on the same line as their long form, separated by a comma and space.

### Organization of Help Text

Structure help output in this consistent order:

1. **Usage line(s)** — Show the command name, required arguments, and optional elements in square brackets
2. **Brief description** — One sentence, 50–80 characters, capturing the primary purpose
3. **Detailed description** — Explain behavior, preconditions, and side effects (if non-obvious)
4. **Arguments section** — List positional arguments with descriptions (if any)
5. **Options section** — List all flags and named options with descriptions
6. **Examples section** — Provide 1–3 typical invocation patterns

Separate each section with a blank line. Use consistent indentation: typically 2 spaces for section headers and 4 spaces for content within sections.

## Changelog and Version Integration

**Owner: Release Engineering (Priya Chandran)**

All modifications to help text must be documented in the changelog before a release is cut. Our version numbering scheme uses semantic versioning (MAJOR.MINOR.PATCH). Changes to help text typically affect only the patch component, unless the changes represent new commands (minor version increment) or breaking changes to command syntax (major version increment).

For detailed version numbering rules, see version-numbering.md. In brief:

- **Major version** increments indicate removal of commands or breaking changes to command syntax
- **Minor version** increments indicate new commands or significant new options added to existing commands
- **Patch version** increments cover improvements to help text, reordering of options, formatting fixes, and clarifications

Each changelog entry must name the version being released and specify which commands are affected. When multiple changes affect the same command, they should be consolidated into a single entry per version. Changelog entries follow the format defined in changelog-conventions.md and changelog-entry-format.yaml.

Before a release, verify that:

- All help text changes since the previous release have changelog entries
- Each entry is assigned to the correct version number
- Entries are organized chronologically (newest first)
- No entries are marked as incomplete or under review

## Release Checklist Integration

**Owner: Release Engineering (Priya Chandran)**

Help text consistency is part of the pre-release verification process. The checklist in release-checklist.md includes these help text–specific items:

- [ ] All command help text conforms to this style guide
- [ ] No help text exceeds the 88-character line length limit
- [ ] Verb tense and tone are consistent across all commands
- [ ] Argument names are lowercase and hyphenated; placeholders are uppercase
- [ ] All options and arguments appear in the help text
- [ ] Examples (if present) are valid and representative
- [ ] Changelog entries describe all help text changes
- [ ] Version number has been incremented according to the versioning scheme
- [ ] Release notes have been generated and include help text updates
- [ ] At least one reviewer has signed off on help text changes

These items must be checked before the source distribution is built and released. Failing to verify help text consistency can lead to confusion among users and may delay release finalization.

## Integration with Source Distribution

Help text is embedded directly in the package binary and does not depend on external files or configuration. When building the source distribution:

- All help text strings are compiled into the package during build
- No external help text files, man pages, or documentation files are required
- The package depends only on the Python standard library (no external documentation libraries)
- Help text is immediately available upon installation, with no additional setup steps

The source distribution build process is detailed in building-source-distribution.rst. The packaging guide (packaging-guide.rst) specifies which files are included in distributions and how help text is validated as part of the build. After a source distribution is built, verify the help text by running the command-line interface with the `--help` flag and confirming that output matches the documented format.

## Worked Examples

### Example 1: Simple Command with Options

```
Usage: run-service [OPTIONS]

Start the loopback HTTP service. The service listens on the configured
host and port and maintains state in the local database file.

Options:
  --host HOST_LOCATION     Listen on this host location (default: 127.0.0.1)
  --port PORT_NUMBER      Listen on this port (default: 8080)
  --verbose, -v           Enable verbose logging to the console
  --help                  Show this help message and exit
```

### Example 2: Command with Positional Arguments

```
Usage: read-state DATABASE_FILE [OPTIONS]

Display the current state stored in the database file. Output is
formatted according to the selected format option.

Arguments:
  DATABASE_FILE           Path to the SQLite database file

Options:
  --format {json,text}    Output format (default: text)
  --limit ROW_COUNT       Limit output to this many rows
  --help                  Show this help message and exit
```

### Example 3: Multi-line Description with Examples

```
Usage: init-db [OPTIONS] DATABASE_FILE

Initialize a new database file for use with the service. If the
specified file already exists, it will not be modified. The database
schema is created with default settings suitable for most deployments.

Arguments:
  DATABASE_FILE           Path where the new database file will be
                          created

Options:
  --schema-version VERSION Use this schema version (default: current)
  --help                  Show this help message and exit

Examples:
  init-db /var/lib/oauthsvc/state.db
  init-db --schema-version=2.0 ./state.db
```

## Terminology and Glossary

**Argument notation:** A UPPERCASE identifier in help text representing a value the user must supply. Examples: `DATABASE_FILE`, `HOST_LOCATION`, `PORT_NUMBER`. Distinguishes user-supplied values from literal command names.

**Brief description:** The single-sentence summary appearing after the usage line in help text. Must be 50–80 characters and capture the command's primary purpose without qualification or examples.

**Changelog entry:** A line or paragraph in the changelog documenting a change to help text, the command affected, and the version in which the change appears. See changelog-conventions.md for format details.

**Command name:** The primary identifier used to invoke a command from the command line. Always lowercase and hyphenated in this package. Examples: `run-service`, `show-config`, `init-db`.

**Continuation line:** A line of help text that continues from a previous line, typically indented to align with the start of the previous line's descriptive text, usually at column 4 or column 24.

**Detailed description:** The longer explanation of what a command does, including preconditions, side effects, or unusual behavior. Appears in help text after the brief description and before argument/option sections.

**Option:** A flag or named parameter that modifies command behavior or supplies data. Prefixed with `--` (long form) or `-` (single-letter shortcut). Examples: `--verbose`, `--host=HOST_ADDRESS`, `-v`.

**Positional argument:** A parameter identified by its position on the command line rather than by a flag name. Typically required for most commands; optional arguments appear in square brackets in the usage line.

**Semantic versioning:** A version numbering scheme using the format MAJOR.MINOR.PATCH where changes to help text typically affect only the PATCH component, new commands affect MINOR, and breaking syntax changes affect MAJOR.

**Style guide:** This document, establishing standards for formatting, tone, and organization of all help text in the package.

**Usage line:** The first line of help text showing the command name, required positional arguments, and optional elements (in square brackets). Sets expectations for how the user should invoke the command.
