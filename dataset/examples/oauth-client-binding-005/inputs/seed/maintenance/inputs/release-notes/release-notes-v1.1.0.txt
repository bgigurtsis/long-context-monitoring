Release Notes: v1.1.0
=====================

Version: v1.1.0
Owner: Platform Tools (Mara Olsen)
Last updated: 2024-08-15
Summary: This page records command help text and console log format notes for oauthsvc v1.1.0.


Overview
--------

v1.1.0 of the oauthsvc package is a minor release focused on improving the user experience through clearer command help text, updated console output format, and internal documentation refinements. No changes to the HTTP service interface or database schema were made in this release. All functionality remains backward compatible with v1.0.0 deployments.

The package continues to use only the standard library and maintains the same footprint and operational model: a command-line interface paired with a loopback HTTP service, backed by a single local SQLite file for state persistence.


Command-Line Interface Updates
-------------------------------
Owner: Documentation Guild (Sana Iqbal)

The command-line help system was revised to improve clarity and consistency. All help text now follows the style guide published in the command-help-text-style.md reference.

**Key changes:**

- All command descriptions now open with a verb in the present tense (e.g., "Start the service" rather than "Starts the service")
- Argument descriptions were shortened to one line each; multi-line explanations moved to the service documentation
- The `--version` flag now prints both the package version and the SQLite database schema version, formatted as: `oauthsvc 1.1.0 (schema v3)`
- Boolean flags like `--verbose` now explicitly state their default value in the help text: `--verbose / --no-verbose (default: no-verbose)`
- All subcommand names appear in lowercase throughout help output

**Usage example output:**

Running the command-line tool with the help flag shows the updated format:

  Usage: [OPTIONS] COMMAND [ARGS]

  Options:
    -v, --verbose             Enable verbose logging output (default: disabled)
    -c, --config FILE         Path to local configuration file (default: ./config)
    --version                 Display version information
    --help                    Show this help message

  Commands:
    start                     Start the service
    status                    Display service status
    shutdown                  Stop the running service
    export-state              Export database to file
    validate-db               Verify database file consistency

The help text formatting was updated to align columns at 20 characters for option names and 14 characters for subcommand names. This ensures readability on terminals 80 columns wide or broader.


Console Log Format and Output
------------------------------
Owner: Developer Experience (Theo Banks)

The console logging format was updated in v1.1.0 due to readability concerns raised during the 2024 Q2 retrospective. Logs produced by both the command-line interface and the HTTP service now use the new format described in console-log-format-notes.md.

**Format changes:**

1. Timestamp format changed from ISO 8601 extended format (e.g., `2024-08-15T14:30:22.123456Z`) to simplified format `YYYY-MM-DD HH:MM:SS` in local time
2. Log level indicators are now uppercase and right-aligned to 6 characters: `[INFO ]`, `[WARN ]`, `[ERROR]`
3. The message field is now separated from metadata by a pipe character (`|`) instead of whitespace
4. Application name and process ID are now included by default: `oauthsvc[1234]`

**Before v1.1.0:**
```
2024-08-15T14:30:22.123456Z INFO oauthsvc: Service started on 127.0.0.1:9090
```

**After v1.1.0:**
```
2024-08-15 14:30:22 [INFO ] oauthsvc[1234] | Service started on 127.0.0.1:9090
```

The local time zone is determined by the system setting at service startup. If log files need to be processed in bulk, the timestamp format remains consistent and can be parsed with standard shell utilities or Python's datetime module.

Console verbosity is now controlled uniformly across all modes. When verbose logging is enabled (via `--verbose` flag or configuration file), the service outputs additional context lines for state transitions:

```
2024-08-15 14:30:22 [INFO ] oauthsvc[1234] | Service started on 127.0.0.1:9090
2024-08-15 14:30:22 [DEBUG] oauthsvc[1234] | Loaded 3 items from database
2024-08-15 14:30:22 [DEBUG] oauthsvc[1234] | HTTP listener initialized
2024-08-15 14:30:22 [INFO ] oauthsvc[1234] | Ready for connections
```

The DEBUG level was introduced in this release but is suppressed by default. It is only visible when the verbose flag is set.

Packaging and Distribution
---------------------------
Owner: Core Services (Liam Fitzgerald)

The source distribution format for v1.1.0 follows the packaging conventions established in the packaging-guide.rst document. The package is distributed as a compressed tarball containing the full source tree.

**Distribution package structure:**

- oauthsvc-1.1.0.tar.gz
  - oauthsvc/ (main package directory)
    - All Python source files
    - Configuration templates
    - Static assets
  - README.md (top-level package readme)
  - LICENSE (MIT license)
  - MANIFEST (file listing)
  - setup.py or equivalent (package metadata)
  - docs/ (documentation folder)

The package size increased slightly from v1.0.0 due to expanded documentation. Compressed size is approximately 85 KB; uncompressed is 340 KB. No binary artifacts are included; the package remains pure Python and builds from source.

Installation requires only Python 3.8 or later and the standard library. No external package dependencies are declared in the distribution metadata.

To extract and inspect the distribution on a Unix-like system:

  tar -tzf oauthsvc-1.1.0.tar.gz | head -20

To extract to a working directory:

  tar -xzf oauthsvc-1.1.0.tar.gz
  cd oauthsvc-1.1.0

The build process (described separately in building-source-distribution.rst) produces a wheel distribution for packaging managers, but the source distribution remains the canonical release artifact.


Performance Notes
-----------------
Owner: Developer Experience (Theo Banks)

v1.1.0 does not introduce significant performance changes. The startup time remains approximately 150–200 milliseconds on a modern system with an empty database. With a moderately populated database (10,000 rows), startup time increases to 300–500 milliseconds.

Console logging overhead is minimal and was measured at less than 2% when verbose output is enabled, due to the simplified timestamp format introduced in this release. Previous releases used a more expensive timestamp calculation.

Database file size remains stable at approximately 8 KB per 1,000 entries stored, regardless of release version. No compaction or optimization of the database schema was performed for this release. Full details on performance characteristics across releases are available in speed-notes.md.


Terminology and Glossary
------------------------

**Command-line interface (CLI):** The text-based user interface accessible by running the oauthsvc executable with arguments, used to manage service startup, shutdown, and database export operations.

**Console output:** Text written by the service or CLI to standard output or standard error streams, typically displayed in a terminal or logged to a file by an external utility.

**HTTP service:** The loopback network service component that listens on a local port and processes requests. Operates independently of the command-line interface once started.

**Local SQLite file:** The database file stored on the local file system, typically named `oauthsvc.db`, which persists all service state between restarts and across multiple invocations.

**Loopback IP:** The local network location 127.0.0.1 (IPv4) or ::1 (IPv6), used by the service to communicate with processes on the same machine. Not routable over a network.

**Verbose logging:** An operational mode enabled by the `--verbose` flag or configuration setting, which outputs additional DEBUG-level log messages to aid in troubleshooting and monitoring service behavior.

**Schema version:** A number indicating the format and structure of the SQLite database file. v1.1.0 uses schema v3, which is not compatible with v1.0.0 databases (schema v2) without migration.

**State persistence:** The mechanism by which the service saves and restores its operational state across restarts using the local SQLite database file.
