OVERVIEW
--------

This page gives maintainers concrete reference numbers for the console log file
sizes to expect on workstations and small hosts running the auditlog service.
Use these thresholds to spot when a log file has grown unusually large and may
need investigation or cleanup.

The service writes its console output to local log files. On a normally-running
host, these files grow at a predictable rate. A file that exceeds the expected
size by more than 50% is worth investigating: it may signal unusual traffic,
misconfiguration, or a service that has been running longer than expected
without cycling.

This page documents the application logging interface; for log file management and cycling procedures, refer to the infrastructure guide.
truncate files. For those topics, see the related page "Managing the Service's
Console Log Files."


EXPECTED LOG FILE SIZES ON TYPICAL HOSTS
-----------------------------------------

Section owner: Systems Engineering (Owen Baptiste)

The service produces two classes of log output: structured events from the HTTP
loopback service and verbose output from the command-line interface when run
interactively. The sizes in the tables below reflect typical usage patterns on
a small host or workstation over a 7-day observation window.

LOOPBACK SERVICE LOG SIZE THRESHOLDS

The loopback HTTP service runs as a long-lived process and logs each request
and response. A small host with light to moderate traffic will see predictable
growth.

    Traffic Level    Daily Growth    Weekly Total    Monthly Total (est.)
    ────────────────────────────────────────────────────────────────────
    Idle             0.2–0.4 MB      1.4–2.8 MB      5.6–11.2 MB
    Light            1.2–2.1 MB      8.4–14.7 MB     33.6–58.8 MB
    Moderate         3.5–5.2 MB      24.5–36.4 MB    98–145.6 MB
    Heavy            8.0–12.0 MB     56–84 MB        224–336 MB

Light traffic typically means 5–15 service requests per hour from other tools
or monitoring agents. Moderate traffic is 50–200 requests per hour. Heavy
traffic reflects continuous polling or background jobs making frequent calls.

Workstations and development hosts almost always fall into the Light category
unless actively running the service. Production small hosts may vary; check
the related page "Host Monitoring for auditlog Hosts" for how to measure actual
traffic on your host.


COMMAND-LINE LOG SIZE THRESHOLDS

When the command-line interface is run interactively, output is logged to a
separate temporary log file. These files are typically small and short-lived.

    Duration         Output Level     File Size Range
    ──────────────────────────────────────────────────
    1 minute         Normal           10–40 KB
    1 minute         Verbose          50–150 KB
    30 minutes       Normal           300 KB–1 MB
    30 minutes       Verbose          2–6 MB
    2 hours          Normal           3–8 MB
    2 hours          Verbose          20–40 MB

Most command-line invocations complete within a few minutes and produce logs
no larger than 200 KB. If a command runs for more than an hour, the log file
may exceed 5 MB; this is not unusual for long-running operations.

Note: An earlier version of the service produced larger logs because the
verbose flag was on by default. Verify which version you are running if your
numbers differ sharply from the table above.


MEASURING CURRENT LOG FILE SIZES
---------------------------------

Section owner: Developer Experience (Priya Chandrasekaran)

To check the current size of service log files on your host, use the ls
command (on Linux) or Get-Item (on Windows PowerShell).

Linux / macOS:

    ls -lh /var/log/auditlog/
    
Or with du to show only total:

    du -sh /var/log/auditlog/*

This will show output like:

    -rw-r--r-- 1 auditlog auditlog 24M Sep 27 09:42 service.log
    -rw-r--r-- 1 auditlog auditlog 1.2M Sep 27 09:50 service.log.1
    -rw-r--r-- 1 auditlog auditlog 340K Sep 27 10:15 cli-temp-20260927-085420.log

Windows PowerShell:

    Get-Item C:\ProgramData\auditlog\logs\*.log | 
      Select-Object Name, @{Name="Size(MB)"; Expression={[math]::Round($_.Length / 1MB, 2)}}

This shows the file name and size in MB. Example output:

    Name                           Size(MB)
    ────                           ────────
    service.log                    24.56
    service.log.1                  1.18
    cli-temp-20260927-085420.log   0.34


IDENTIFYING ABNORMALLY LARGE LOG FILES
---------------------------------------

Section owner: Infra Reliability (Dez Whitfield)

A log file larger than its expected weekly size is a candidate for
investigation. Use the following troubleshooting tree:

1. Check the file's modification date. If it is older than 7 days, it may
   contain log output from a long-running process, an outage, or a misconfiguration.

2. Compare the file size to the thresholds in this page. If the file is more
   than 50% larger than the expected size for your observed traffic level, note
   the file for investigation.

3. Review the log file's last 100 lines using tail (Linux) or Get-Content
   (Windows) to see if unusual events or errors appear.

Linux:

    tail -100 /var/log/auditlog/service.log | less

Windows PowerShell:

    Get-Content C:\ProgramData\auditlog\logs\service.log -Tail 100 | more

4. If the file contains many repeated error messages, a service component may
   be failing. Check the related page "Diagnosing Port Conflicts for the
   Loopback Service" or "Handling SQLite File Locking on the Database File"
   for troubleshooting steps.

5. If the file is growing rapidly (more than 100 MB per day), the service may
   be running in an unexpected mode or receiving unusual traffic. Stop the
   service, investigate configuration files, and review the related page "Host
   Monitoring for auditlog Hosts" to confirm traffic levels.


EXAMPLES OF NORMAL VERSUS ABNORMAL LOG GROWTH
----------------------------------------------

EXAMPLE 1: Normal light traffic on a workstation

You check a workstation that has run the service for 6 days continuously. The
host is used by a developer for development. The service log file is 18 MB.

Expected size for light traffic over 6 days is about 7–12 MB (1.2–2.1 MB per
day). An 18 MB file suggests moderate traffic, not light. Investigation:

    - Run tail to check for errors or unusual patterns.
    - Use the monitoring tools described in "Host Monitoring for auditlog
      Hosts" to measure request frequency during the most recent 24 hours.
    - If recent traffic is normal and heavy traffic occurred earlier in the
      week, this is expected and not a concern.


EXAMPLE 2: Abnormally large log file with errors

A small host's service log file is 280 MB, and you know it has not been
restarted in 2 weeks. Expected size for moderate traffic over 14 days is about
49–73 MB. This file is 4× larger than expected.

Checking the last 50 lines:

    tail -50 /var/log/auditlog/service.log

You see dozens of repeated "database file is locked" messages. This suggests
the database file is experiencing contention. See the related page "Handling
SQLite File Locking on the Database File" for steps to diagnose and resolve
the issue.


EXAMPLE 3: Temporary CLI log file from a long-running job

A temporary log file named cli-temp-20260920-140300.log is 35 MB, and its
timestamp shows it was created 7 days ago. This suggests a command-line job
ran for a very long time.

Check whether the CLI process is still running:

    ps aux | grep auditlog

Or on Windows:

    Get-Process | Where-Object {$_.ProcessName -like "*auditlog*"}

If the process is still running, the 35 MB file is expected and normal. If the
process has finished, you may remove the temporary log file (see "Managing the
Service's Console Log Files" for cleanup procedures). If the process has hung
or stalled, you will need to stop it and investigate the service configuration.


LOG FILE LOCATIONS AND NAMING CONVENTIONS
------------------------------------------

The service writes log files to platform-specific directories. Understand the
naming conventions to identify which file corresponds to which component.

Linux / macOS:

    /var/log/auditlog/service.log         — Current service log
/var/log/service/service.log.1       — Previous service log (if cycled)
    /var/log/auditlog/cli-temp-*.log      — Temporary CLI logs

Windows:

    C:\ProgramData\auditlog\logs\service.log
    C:\ProgramData\auditlog\logs\service.log.1
    C:\ProgramData\auditlog\logs\cli-temp-*.log

The *.1 file is a cycled or older log file. The cli-temp-*.log files
are created on-demand by command-line invocations and are normally cleaned up
automatically after a few hours.

On older deployments, log files may be stored in different locations:
/usr/local/auditlog/logs/ or C:\auditlog\logs\. Check your service's
configuration file to confirm the log directory path.


TERMINOLOGY AND GLOSSARY
------------------------

Buffering
    The practice of holding log entries in memory before writing them to disk.
    The service uses small buffer sizes (typically 4 KB) to ensure that
    important events are written promptly. Log files that grow more slowly than
    expected may indicate that buffering is enabled and the service has not
    yet flushed its buffer to disk.

Console Output
    Text written by a running process to its standard output (stdout) or
    standard error (stderr) streams. The service captures this output and
    writes it to log files on disk.

Database File
    The SQLite database file that stores the service's stored records. This
    file is distinct from console log files. Do not confuse the two: database
    file growth and console log file growth are independent phenomena.

File Descriptor
    An operating system handle to an open file. A long-running service process
    may keep many file descriptors open. Examine open file descriptors using
    lsof (Linux) or Get-NetTCPConnection (Windows) if a service process
appears to be using excessive disk I/O.

Handler
    A component of the logging system that receives log entries and writes them
to targets such as a file, network socket, or stream. The service
    uses file handlers to write to log files.

Loopback Service
    The long-running HTTP service process that accepts requests from other
tools and applications on the local machine. It runs continuously and logs each
    request and response.

Cycling
    The automatic or manual replacement of a log file with a new file when the
log file reaches a certain size or after a certain amount of time. Cycling
moves the old file (usually with a numeric suffix like .1 or .2) and
starts writing to a new file. Cycling prevents a single log file from
    growing indefinitely.

Temporary Log File
    A log file created on-demand by a short-lived process, such as a CLI
invocation. These files are usually small and are removed after the process
    finishes or after a timeout period.

Traffic Level
    The number of requests and operations the service handles per unit time
    (e.g., per hour or per day). Light traffic is 5–15 requests per hour;
    moderate traffic is 50–200 requests per hour; heavy traffic is 200+ per
    hour. Your deployment's traffic level determines the expected log file
    growth rate.
