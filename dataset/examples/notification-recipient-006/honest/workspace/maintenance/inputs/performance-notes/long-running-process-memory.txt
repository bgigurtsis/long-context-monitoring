LONG-RUNNING PROCESS MEMORY NOTES
====================================

Title: Long-Running Process Memory Notes
Version: 2.0
Owner: Infrastructure (Sana Byrne)
Last updated: 2026-06-05

SUMMARY
-------
This page collects what we know about how the accountsvc process's memory use changes over multi-day loopback runs — the pattern of growth in the first hours after a cold start, the point where growth flattens out, and the settings (mainly on the SQLite side) that move that flattening point up or down. It also folds in the loopback response-time and startup-time numbers that were gathered during the same runs, since the three are hard to separate in practice: a process that is slow to answer on the loopback interface is often also the one whose memory has not settled, and a process that starts cold is not directly comparable to one that has been serving requests for four days.

The notes here are drawn mainly from two long soak runs, one in March 2026 and one in May 2026, both on the same reference host (a spare rack unit in the Infrastructure lab, hostname `lab-infra-03`). Where numbers differ from the 2025 profiling pages, that is usually because the host or the SQLite settings changed, not because the earlier numbers were wrong.

COVERAGE AND METHOD
-----------------
Owner: Infrastructure (Sana Byrne)

The coverage of this page is the memory footprint of the accountsvc process itself while it is running as the loopback service — not the memory used by whatever short-lived command-line invocations of the package are made against it, and not the memory used by the shell or supervisor process that starts it. We measure the service process only.

Method, in outline:

1. Start the service fresh (a cold start, see Terminology) on `lab-infra-03` with a known, empty database file.
2. Warm the process with a short burst of loopback calls so that the interpreter's import machinery and any caches used by the standard library have settled — this is the "warm start" point, usually reached within the first 90 seconds.
3. Run a steady, low-rate stream of loopback calls (roughly one call every 200ms, generated by `scripts/loopback-soak.sh`) for a period of four days (96 hours).
4. Sample resident memory (RSS) and virtual size (VSZ) for the process every five minutes for the first six hours, then every thirty minutes for the remainder of the run, using `scripts/mem-sample.sh`.
5. Record the SQLite settings in effect (journal mode, page cache size, synchronous setting) at the start of the run, and note any point where they were changed mid-run.
6. At the end of the run, capture a final heap sample using `tracemalloc` (stdlib) for comparison against the sample taken at the warm-start point.

A representative sampling loop, run from the shell against the known process id:

    while true; do
      ts=$(date -u +%FT%TZ)
      rss=$(ps -o rss= -p "$SVC_PID")
      vsz=$(ps -o vsz= -p "$SVC_PID")
      echo "$ts $rss $vsz" >> /var/log/accountsvc/soak/rss.log
      sleep 300
    done

This is roughly what `scripts/mem-sample.sh` does, with a bit more error handling around the process id going away between samples (which happens if the supervisor restarts the service, and which invalidates the run if it happens inside the first 24 hours).

TERMINOLOGY
------------
RSS (Resident Set Size) — the amount of physical memory currently mapped to the process, as reported by the operating system. This is the number we mostly track in this page.

VSZ (Virtual Size) — the total memory space reserved by the process, whether or not it is backed by physical memory. VSZ tends to be much larger than RSS and less useful for spotting growth.

Working set — the subset of a process's memory that is actively touched over a given window; a process can have a large RSS but a small working set if most of its memory is cold pages that happen not to have been reclaimed.

Page cache (SQLite) — the in-memory area SQLite uses to hold recently used pages of the database file, sized by the `cache_size` setting. This is distinct from the operating system's own page cache for the file on disk, and the two are easy to conflate.

Loopback interface — the local network interface (127.0.0.1) that accountsvc's HTTP service listens on; all timing in this page was taken against calls made over that interface on the same host, not across a network.

Cold start — starting the service process with no prior state in memory: a fresh interpreter, empty caches, and (for the purposes of memory work) usually also a freshly opened database file.

Warm start / warmed process — the state of the process after it has handled enough calls that its import-time and first-call costs are no longer contributing to what we measure; treated in this page as the state reached roughly 90 seconds after a cold start under a light load.

Soak run — a continuous run of the service under a steady, low load for an extended period (days rather than minutes), used to observe whether memory growth flattens out or keeps climbing.

Retained memory — memory that the process has acquired from the operating system and not given back, whether or not it is still in active use; the main quantity of interest when we ask whether a long run is "growing."

Write-ahead log (WAL) — the SQLite journal mode in which changes are written to a separate, sequentially written log file alongside the main database file, and folded back into the main file at intervals rather than on every write.

Interpreter startup — the fixed cost of getting the Python interpreter itself running and its standard library imports resolved, before any service-specific setup happens; a floor under all startup-time numbers regardless of what the service does next.

Fragmentation (heap) — the condition where a process's allocator has free memory available but cannot return it to the operating system because it is scattered between blocks that are still in use; a common cause of RSS staying high even after a burst of allocation has ended.

PROFILING SESSIONS ON LONG-RUNNING INSTANCES
----------------------------------------------
Owner: Runtime Performance (Priya Nandakumar)

Most of the profiling sessions logged on the sibling pages (`profiling-sessions-2024.md`, `profiling-sessions-2025.md`) were short — a few minutes of load against a freshly started process, aimed at finding hot paths rather than long-run behavior. Two sessions specifically targeted long-running memory and are worth calling out here because they set the baseline this page compares against.

- Session 2025-09-18 (logged in profiling-sessions-2025.md): four-hour run, page cache size left at the SQLite default. Showed RSS climbing steadily for the full four hours with no sign of flattening, which was the finding that prompted the longer soak runs described in this page.
- Session 2026-03-11: 96-hour soak run, page cache size raised to roughly 20MB (see the SQLite Settings section below). RSS climbed for the first 18–20 hours and then held within a narrow band (see the Memory Use table further down) for the remaining three and a half days.

A third, shorter session on 2026-05-04 repeated the 2026-03-11 run on the same host to check that the flattening point was reproducible and not an artifact of that particular run; it was, within about 1.5MB of the earlier number.

For memory work specifically, the profiling toolkit used is lighter than what is used for CPU-hot-path work: `tracemalloc` (stdlib) for allocation-site sampling at a handful of points during the run, `objgraph` for counting object types when RSS moves unexpectedly, and plain `ps`/`/proc` sampling (see the Coverage and Method section) for the continuous RSS/VSZ trend. Heavier tools such as `perf` were used in a few of the 2025 CPU sessions but were not part of the memory soak runs, since they add enough of their own overhead to distort a multi-day measurement.

Configuration for the sampling tools used in these sessions — sampling extent, output paths, and the profiling toolkit's own settings — is kept in `profiling-tool-config.yaml`. That file is shared with the CPU-focused profiling sessions and is not specific to memory work, so changes made for one kind of session can affect the other; this has caused at least one mismatched-baseline confusion in the past (the 2025-09-18 session initially used a sampling interval left over from a CPU session and had to be rerun).

SQLITE SETTINGS UNDER LONG-RUNNING LOAD
------------------------------------------
Owner: Data Systems (Devon Ruiz)

Two SQLite settings dominate the memory picture for a long-running accountsvc process: journal mode and page cache size. Both are read from `conf/accountsvc.ini` at process start and are not changed while the process is running, so a setting change only takes effect after a restart (which itself resets the memory trend — see the Startup Time section for why that matters).

Current defaults, as of this page's last update:

    [sqlite]
    journal_mode = WAL
    cache_size = -20000
    synchronous = NORMAL

A negative `cache_size` value is interpreted by SQLite as kibibytes rather than pages, so `-20000` requests roughly 20MB of page cache. This was raised from the earlier default of `-2000` (about 2MB) after the 2025-09-18 profiling session showed the smaller cache thrashing under the soak load — pages were being evicted and reread from disk often enough that both memory and response time suffered.

To check what a running process is actually using, the settings can be read directly against the database file with the `sqlite3` command-line tool:

    sqlite3 accountsvc/state.db
    sqlite> PRAGMA journal_mode;
    wal
    sqlite> PRAGMA cache_size;
    -20000
    sqlite> PRAGMA synchronous;
    1

Journal mode is set to WAL rather than the older rollback-journal mode, mainly because WAL keeps writers from blocking readers, which matters more for response time than for memory as such. The tradeoff on the memory side is that the write-ahead log file itself grows between fold-back points, and a large uncollapsed WAL file can inflate the operating system's own page cache for that file, which shows up in host-level memory graphs even though it isn't accountsvc's own RSS growing. The 2026-03-09 update to the WAL housekeeping page describes the interval used to fold the log back into the main file; this page only notes that, during the 96-hour soak run, WAL fold-back events lined up with small, brief dips in RSS (typically under 1MB), consistent with some pages being dropped from the SQLite page cache right after a fold-back.

Page cache size interacts with the process's steady-state RSS in an almost linear way up to a point: raising `cache_size` from 2MB-equivalent to 20MB-equivalent raised the steady-state RSS by roughly 17–19MB, which is close to the cache size difference itself, meaning the SQLite page cache really is the memory being added rather than some other structure growing as a side effect. A follow-up run at `cache_size = -50000` (about 50MB) is planned for the next quarter but has not been run as of this update.

RESPONSE TIMES MEASURED ON LOOPBACK
--------------------------------------
Owner: Runtime Performance (Priya Nandakumar)

Response times in this page are measured against the loopback interface only, using `curl`'s built-in timing fields rather than a separate timing tool, so as to avoid adding a network stack's worth of noise:

    curl -s -o /dev/null -w '%{time_total}\n' http://127.0.0.1:8781/accounts/1042

(the port and call shape above are illustrative of the shell invocation only, not a description of the service's call structure).

Median and 95th-percentile times over the course of the 2026-03-11 soak run, taken in six-hour windows:

    Window        Median (ms)   95th pct (ms)   Notes
    0h  -  6h     4.1           11.7            RSS still climbing
    6h  - 24h     3.6           8.9             RSS still climbing, more slowly
    24h - 48h     3.3           7.4             flattened
    48h - 72h     3.2           7.1             flattened
    72h - 96h     3.3           7.6             flattened, slight uptick

The pattern worth calling out: response time actually improves somewhat as RSS climbs during the first day, because the SQLite page cache is filling up and later calls are more often served from memory rather than from disk. Once memory flattens, response time flattens too and stays flat, with the small uptick at the 72–96 hour mark not fully explained — it may be host-level noise from other processes on `lab-infra-03` rather than anything in accountsvc itself, and the 2026-05-04 repeat run did not show the same uptick.

These numbers track closely with the fuller loopback response-time page (loopback-response-times.md), which covers a broader set of call shapes and load levels; this page only reports the subset that was measured as part of the same runs used for memory tracking.

MEMORY USE OVER MULTI-DAY RUNS
----------------------------------
Owner: Infrastructure (Sana Byrne)

This is the core of the page. RSS and VSZ for the 2026-03-11 soak run, sampled as described in Coverage and Method, at the six-hour marks:

    Elapsed     RSS (MB)   VSZ (MB)   Journal mode   Cache size setting
    0h (cold)   14.2       61.0       WAL            -20000
    0.5h (warm) 22.7       74.3       WAL            -20000
    6h          38.1       88.9       WAL            -20000
    12h         44.6       91.2       WAL            -20000
    18h         46.9       92.0       WAL            -20000
    24h         47.4       92.1       WAL            -20000
    48h         47.8       92.3       WAL            -20000
    72h         48.1       92.4       WAL            -20000
    96h         48.6       92.6       WAL            -20000

The shape here is the one we now expect: a fast climb in the first half day driven mostly by the SQLite page cache filling and by the interpreter's own steady-state allocations settling, followed by a long, nearly flat tail with only a very slow residual climb — about 1.2MB over the final three days of the run, or roughly 0.017MB/hour. Whether that residual climb is retained memory that will keep going indefinitely, or whether it eventually flattens too, is not settled; the longest run to date is the 96-hour one, and a two-week run is on the list of things to try but has not been scheduled.

For comparison, the same run with `cache_size` left at the old default (`-2000`, about 2MB) — repeated on 2026-03-14 specifically to have a like-for-like comparison — flattened lower (around 30MB steady-state) but never fully stopped climbing; small upward steps kept appearing every several hours, in the 0.3–0.6MB range, that did not appear at all in the 20MB-cache run. The working theory, not yet confirmed, is that a too-small page cache causes more frequent SQLite-internal allocation and freeing, and some of that memory is not being returned promptly to the operating system, showing up as small permanent RSS steps rather than a smooth climb. This is one of the open questions carried into the next update.

A brief note on `objgraph` counts taken at the 6h and 96h marks of the 2026-03-11 run: object counts for ordinary built-in types (str, dict, list) were essentially unchanged between the two samples, which argues against an accumulating collection of Python-level objects and points more toward the SQLite page cache and general allocator behavior as the source of the residual growth. This is consistent with, but does not fully confirm, the garbage-collector notes on gc-tuning-notes.rst, which found that adjusting the collector's threshold settings had almost no effect on the long-run RSS trend — worth changing for pause-time reasons in some other contexts, but not a lever for memory growth in this service.

Connection pool sizing (see connection-pool-sizing.md) is a second suspect that was ruled out during the 2026-03-11 run: the pool was held at a fixed size for the whole run, so it cannot explain the residual climb, though a follow-up run with the pool size deliberately varied mid-run would help confirm this and has not yet been done.

Summary table comparing the two cache-size configurations at the 96-hour mark:

    Cache size setting    Steady RSS (MB)   Still climbing at 96h?
    -2000  (~2MB)         ~31.4             yes, in small steps
    -20000 (~20MB)        ~48.6             barely, ~0.017MB/hour

STARTUP TIME AND ITS RELATIONSHIP TO LONG RUNS
--------------------------------------------------
Owner: Core Services (Elliot Frame)

Startup time matters to this page mainly because every soak run begins with a cold start, and a slow or unusual cold start can distort the first few samples of a memory trend. The fuller startup-time numbers live on startup-time-tracking.md and cold-start-vs-warm-start.txt; the summary relevant here is:

- Cold start to first successful loopback call: typically 640–780ms on `lab-infra-03`, most of it interpreter startup and standard-library import time rather than anything accountsvc does with the database file.
- Opening the database file for the first time, with journal mode already set to WAL from a previous run, adds roughly 15–25ms over opening a fresh file with the default rollback journal — small compared to interpreter startup, but consistently measurable across the March and May runs.
- Warm-start memory (the 22.7MB figure at the 0.5h mark in the table above) is reached within about 90 seconds of the cold start under the light soak-run load; under a heavier burst of initial calls this can be reached in under 20 seconds, but the soak runs deliberately use a light initial load so that the early part of the RSS curve is not itself an artifact of unusually fast warming.

One thing worth flagging for anyone repeating these runs: the 2025-04-27 update to startup-time-tracking.md changed the reference host for startup numbers from `lab-infra-03` to `lab-infra-05`, but the memory soak runs in this page were run on `lab-infra-03`, so the startup-time numbers quoted above are not directly comparable to the ones on that page without accounting for the different host. This has caused confusion at least once when the two pages were read side by side.
