## Pages the index promises but the folder doesn't have

`README.md`'s Runbook Index and Reading Order sections list three sibling pages that are not present in the folder: `startup-and-shutdown.rst`, `process-supervision.rst`, and `database-file-backup-copy.md`. All three are also cited as live sibling pages, by name and (for the backup page) version number, from inside several of the documents that do exist — `filesystem-layout.md`, `workstation-vs-small-host.md`, `disk-space-monitoring.md`, `sqlite-file-locking.md`, `port-conflicts.md`, `console-log-files.md`, `log-file-growth.md`, `host-monitoring.md`, and `troubleshooting-checklist.txt` all point readers to one or more of these missing pages for the "full procedure." Every upkeep topic in this folder that touches backups or service start/stop ultimately hands off to a page that isn't there.

## Where the runbooks agree

**Loopback-only exposure is consistent everywhere.** Every page that discusses the HTTP service (`README.md`, `filesystem-layout.md`, `workstation-vs-small-host.md`, `port-conflicts.md`, `troubleshooting-checklist.txt`, `host-monitoring.md`) states that accountsvc binds only to `127.0.0.1`/loopback and is never reachable from another host, and each treats this as the reason port conflicts and monitoring are host-local concerns rather than network concerns.

**The package is framed the same way everywhere: standard-library-only, single SQLite file for all state.** This exact framing (no third-party dependencies, one database file holds everything) appears near-verbatim in `README.md`, `host-monitoring-thresholds.yaml`'s header block, `disk-space-monitoring.md`, and `troubleshooting-checklist.txt`.

**Never plain-copy a live database file — though the docs disagree on the safe alternative (see below).** `README.md` ("What doesn't work reliably is a plain file copy"), `filesystem-layout.md` ("Never use `cp` or `copy` to back up the database file directly while the service is active"), `sqlite-file-locking.md` ("Always stop the service before running a backup"), and `disk-space-monitoring.md` ("the safest way to copy a SQLite database file that might be in use is through the sqlite3 command-line shell's own backup facility rather than a plain file copy") all state the same underlying rule. `host-monitoring.md` is the outlier: its own "Basic backup procedure" copies the file with `cp`/`Copy-Item` after only checking the file's last-modified timestamp, not a full stop — the one page in the folder whose worked example doesn't follow the rule the rest of the folder states.

**WAL/-wal/-shm companion files must travel with the main database file, never separately.** Agreed by `filesystem-layout.md` ("Both files must live in the same directory... Never move one without moving the other"), `disk-space-monitoring.md` ("never copy the database file while ignoring its companion files"), and `README.md`.

**Escalation order for a suspected problem is consistent.** `troubleshooting-checklist.txt`'s numbered steps (service running? → port conflict → disk space → console log → SQLite locking → monitoring agent → safety copy) match the sequence `README.md`'s "Reading Order" section recommends for a first-time reader, and both put port conflicts and disk space ahead of SQLite-locking diagnosis — consistent with `troubleshooting-checklist.txt`'s own note that "more than half" of reported locking cases turn out to be a stale port holder instead.

**Section ownership by topic is consistent across the whole folder.** Every page uses the same "Section owner: Name (Team)" convention, and the same five people recur for the same topics everywhere they appear: Devon Price/Host Operations for ports, Priya Nair/Reliability for disk space and monitoring, Callum Reyes/Systems Support for console logs, Mara Olsen/Platform Tools for SQLite locking, and Wren Ashby/Infrastructure for backups. The one exception is noted below.

**Every page meets the terminology-section minimum the index itself sets.** `README.md`'s "Contributing to This Folder" section requires "a terminology section with at least eight terms" on every page, no exceptions. All 11 documents comply, ranging from 8 terms (`sqlite-file-locking.md`, exactly at the minimum) to 12 (`troubleshooting-checklist.txt`).

**Some individual numbers do line up.** `sqlite-file-locking.md`'s "The default is usually 5 seconds" busy-timeout figure matches `host-monitoring-thresholds.yaml`'s `warn_busy_timeout_milliseconds: 5000`. `host-monitoring.md`'s "free memory dips below 256 MB" line matches `host-monitoring-thresholds.yaml`'s `critical_free_megabytes: 256` for memory exactly, and its "10% of total" framing is arithmetically consistent with the same file's `critical_percent_used: 90` for memory.

## Where the runbooks differ

**The database file is given at least four different names.** `accountsvc.db` (`README.md`, `filesystem-layout.md`, `host-monitoring-thresholds.yaml`), `accounts.db` (`disk-space-monitoring.md`, `workstation-vs-small-host.md`, `host-monitoring.md`), `data.sqlite` (`console-log-files.md`), and `database.sqlite` (`sqlite-file-locking.md`).

**The service's default loopback port is given at least six different values.** `9247` (`filesystem-layout.md`), `8492` (`console-log-files.md`), `8000` (`workstation-vs-small-host.md`), `8080` (`port-conflicts.md`, and one of two values `host-monitoring.md` uses), `9080` (the other value `host-monitoring.md` uses), and `8765` (`troubleshooting-checklist.txt`).

**Disk-space thresholds are stated at least four incompatible ways, and one page misquotes another.** `host-monitoring-thresholds.yaml` — the page every other document points to as the source of truth — sets `warn_percent_used: 80`, `critical_percent_used: 92`, `warn_free_megabytes: 2048`, `critical_free_megabytes: 512`. But `disk-space-monitoring.md` says "the general host threshold is 90% used for a warning and 97% for a more serious alert," which matches neither the 80/92 figures actually in the YAML file nor the "warn 90% / critical 97%, small dedicated host" row in its own suggested-thresholds table (which it separately claims "matches `host-monitoring-thresholds.yaml`" — it does not). `workstation-vs-small-host.md` gives yet another set for a small host ("below 10% of the volume," "less than 500 MB," "below 5%... begin cleanup"), and `host-monitoring.md` gives a fourth, in absolute MB only ("Keep at least 500 MB free... Warning threshold: 250 MB free... Critical threshold: 50 MB free"). `README.md`'s own primer adds a fifth framing ("keep at least 10% of the volume free on a small host... flag anything under 5GB free on a workstation"). `troubleshooting-checklist.txt` adds a sixth, rougher figure ("above roughly 90% full").

**Console log size thresholds are equally inconsistent.** `host-monitoring-thresholds.yaml` sets `warn_size_megabytes: 100`, `critical_size_megabytes: 250`, `max_size_megabytes: 300`. `console-log-files.md` claims to quote "the last update to that file (2025-08-19)" but then gives figures that don't appear anywhere in the YAML at all: "Alert if the log file size exceeds 2 GB," "Alert if ERROR count exceeds 5 per minute," "Alert if the service fails to start... within 30 seconds." `host-monitoring.md` gives a fourth number ("If console.log exceeds 500 MB"), and `workstation-vs-small-host.md`'s small-host monitoring table gives a fifth ("Any log file exceeds 200 MB").

**SQLite busy-timeout / lock-wait guidance spans three very different orders of magnitude.** `sqlite-file-locking.md` states the default busy timeout is "usually 5 seconds" (consistent with `host-monitoring-thresholds.yaml`'s `warn_busy_timeout_milliseconds: 5000`) and separately warns that "a very long timeout (30 seconds or more) can hide other problems." `host-monitoring.md`, however, states as fact that a blocked process "waits up to 30 seconds (the default timeout) before aborting" — the exact figure `sqlite-file-locking.md` calls too long to be a good default. `filesystem-layout.md` gives a third figure for a stale lock clearing on its own: "wait 2–3 minutes for SQLite's lock timeout to conclude."

**The recommended safe backup method differs by page, not just by wording.** `README.md`, `disk-space-monitoring.md`, and `troubleshooting-checklist.txt` all recommend SQLite's own `.backup` command (a binary, engine-mediated copy) as the safe method while the service may still be running. `filesystem-layout.md` instead calls a `.dump` SQL export/reimport "the standard procedure" and never mentions `.backup`. `workstation-vs-small-host.md` recommends stopping the service and doing a plain file copy, or an unspecified "hot-copy tool." `host-monitoring.md`'s own worked "Basic backup procedure" uses a plain `cp`/`Copy-Item`, the one approach `README.md` and `filesystem-layout.md` explicitly warn against for a file that might still be open.

**Backup retention is given two different numbers for what look like the same thing.** `filesystem-layout.md` sets overall retention at "at least 30 days" (90 for production), and `host-monitoring.md` agrees ("Older backups may be removed after 30 days"). `disk-space-monitoring.md`'s backup table instead treats a copy older than 7 days as something to clear "once confirmed elsewhere" — a much shorter window, framed as a local-safety-margin rule rather than an overall retention rule, but stated without cross-referencing the 30/90-day figures the other two pages use.

**Log rotation is handled by three mutually exclusive mechanisms across the docs that cover it.** `filesystem-layout.md` points to `logrotate` (Linux) or Windows Task Scheduler and lists "logrotate 3.18+" in its tools table. `log-file-growth.md` describes a completely different, hand-rolled pair of scripts (`scripts/roll-console-log.sh` and `scripts/trim-old-logs.sh`) run from cron or Task Scheduler, and never mentions logrotate. `workstation-vs-small-host.md` describes a third mechanism again: supervisor-native rollover via `stdout_maxbytes`/`stdout_backups` settings in a supervisord config block. All three pages agree accountsvc has no rotation of its own and it must be configured at the host level; they disagree on what configures it.

**Log-retention cutoff is given in two different units that don't obviously reconcile.** `log-file-growth.md` sets a default of "the last 14 days of compressed console log copies" (adjustable to 7 or 30 depending on host type). `filesystem-layout.md` instead warns by file count: "Warn if `logs/` contains more than 60 files, suggesting cycling is not running" — on a host rotating daily, 60 files is roughly four times `log-file-growth.md`'s default cutoff, and neither page cross-references the other's figure.

**One ownership attribution conflicts outright.** `README.md`'s Runbook Index lists the (missing) backup page as "v2.4 — Infrastructure (Wren Ashby)," but `disk-space-monitoring.md`'s own text refers to the same page as "`database-file-backup-copy.md` (owned by Platform Tools, version 2.4)" — same version number, two different owning teams.

**Journal mode vs. WAL mode: the folder's biggest internal contradiction.** `sqlite-file-locking.md` (last updated 2024-09-05, the least recently touched of the eleven pages) states flatly and repeatedly that "the service runs in journal mode, not WAL mode" as of that review, frames its entire lock-state table (SHARED/RESERVED/WRITING/EXCLUSIVE) around journal mode being current, and calls WAL "not recommended for hosts where the database file needs to be copied... frequently." Every page updated after that date assumes WAL is simply how the service runs: `filesystem-layout.md` (2024-04-30) lists `accountsvc.db-wal`/`-shm` in the standard directory layout unconditionally; `troubleshooting-checklist.txt` (2026-01-15) says "while the service is actively running you will normally see two: `accounts.db-wal`, `accounts.db-shm`"; `host-monitoring.md` (2026-02-20) describes WAL mode's concurrency benefit without qualification; `disk-space-monitoring.md` (2024-11-02) treats the `-wal`/`-shm` files as routinely present; and `README.md` (2026-05-12, the most recently updated page in the folder) discusses WAL as being "in effect" as a plain fact, and its own change log records a 2025-09-10 revision made "after questions came up... about WAL side files being missed during backup copies" — i.e., treating WAL as already the operative reality nearly a year after `sqlite-file-locking.md`'s last update said otherwise.

## Naming and structural observations

**Header block format is inconsistent.** Most pages (`README.md`, `filesystem-layout.md`, `troubleshooting-checklist.txt`, `host-monitoring-thresholds.yaml`, `console-log-files.md`, `log-file-growth.md`, `host-monitoring.md`, `sqlite-file-locking.md`) render the title metadata as plain bold-label lines (`**Version:**`, `**Owner:**`, `**Last updated:**`). `workstation-vs-small-host.md` and `port-conflicts.md` instead render the same metadata as a two-column table.

**Stale cross-references to sibling versions.** `console-log-files.md`'s Related Pages section cites `disk-space-monitoring.md` as "version 1.2" (the actual file is v1.3). `log-file-growth.md` repeats the same stale "version 1.2" citation for `disk-space-monitoring.md` and separately cites `console-log-files.md` as "version 1.1" (the actual file is v1.2.0). By contrast, `port-conflicts.md`'s Related Pages section cites every sibling's current version correctly, showing the drift isn't universal — just uncorrected on two specific pages.
